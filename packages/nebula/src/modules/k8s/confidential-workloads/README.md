# Confidential workloads

`ConfidentialOperator` installs the `ConfidentialWorkload` and `ConfidentialStorage` CRDs and a namespace-scoped controller. Each workload gets its own SEV-SNP PodVM with the pinned official Trustee Helm chart, TNG, one Nebula agent and the application. Set `agentImage` to the reviewed agent digest. Native CoCo `genpolicy` measures the complete Pod. The operator never receives decryption keys or owner private keys.

The [agent](../../../../../confidential-agent/README.md) has one main entrypoint and shared lifecycle. Owner access, readiness, attestation collateral, browser frontend and preparation are internal modules. Inside a workload guest, it replaces the separate owner, readiness, firewall, launcher-installation, resource-broker and per-volume containers. Its HTTP process drops to UID 10001 before listening. One private native child owns all declared encrypted volumes and approved application-resource sockets with only CHOWN, SYS_ADMIN and MKNOD capabilities.

TNG and the unmodified official Trustee remain upstream components. The Kubernetes controller remains outside the guest. Enrolled declarations using `storageImage` and `trustee.gatewayImage` retain their measured layout; use `agentImage` for new deployments rather than replacing an enrolled guest.

For the browser flow, add a `ConfidentialBrowser` preparation VM and a diskless frontend using `manualTls`. TNG serves the first page with TLS terminating inside the measured guest. The user independently checks the browser's actual certificate and approved workload measurements before entering their token. TNG WASM then verifies the preparation and final workload, with keys released only to their enrolled instances. See the [browser guide](../../../../../confidential-browser/README.md).

An optional `ConfidentialWelcome` adds a normal HTTPS connection guide at a literal public IP. Its own pinned Caddy sidecar handles Let's Encrypt HTTP01 and TLS, with the required `shortlived` certificate profile and automatic renewal; it uses no Ingress, cert-manager, DNS record or shared ingress controller. Set `name`, `namespace`, `ipAddress`, `acmeEmail`, an existing retained filesystem PVC in `acmeClaimName`, and the token-free guest `portalUrl`. Optionally supply `nodeSelector`, public reference measurements and a release URL. The stack's Service maps the supplied address on ports 80/443 to unprivileged Caddy listeners; that address must already route to the cluster, and both ports must be available. No load balancer or public IP is allocated by the module.

Node serves only on guest-independent Pod loopback `127.0.0.1:8081`; Caddy owns HTTP8080/HTTPS8443 and explicitly selects the IP certificate for clients without SNI. Both containers run without root, extra capabilities or Kubernetes credentials. Only Caddy mounts the private ACME state PVC at `/data`; retain that PVC and its backing volume across Pod replacement so account state, certificate keys and renewal information survive. A `Recreate` deployment avoids concurrent writers to the RWO claim. Storage provisioning and a suitable retention policy belong to the owning stack; there is no temporary certificate-state fallback. The public Service includes unready endpoints so the first HTTP01 challenge can succeed before HTTPS readiness. None of this changes confidential guests, their disks or their RA-TLS keys. Give users the guide's `https://<IP>/` URL and the access token separately.

The guide explains independent verification, displays a current reported certificate snapshot, and offers DER/evidence downloads before linking to the RA-TLS portal. Ordinary HTTPS authenticates the guide's IP address; it does not attest the guest. Users must verify and compare the portal's actual browser certificate against independently approved measurements before entering credentials. Optional certificate trust settings vary by browser and may leave hostname or other warnings. The guide never accepts access tokens, passwords, images or registry credentials. Its public API remains limited to one fixed guest-certificate route, with no caller-selected destination or owner API forwarding. For a frontend in the same cluster, set `portalService: { name, namespace }`: the server fetches public material through that ConfidentialBrowser's private Service on10443 and allows only its namespace/browser pod label in network policy. The public portal URL stays unchanged, and this private certificate origin is omitted from `GET /config.json`. Omitting `portalService` retains the external public-origin relay.

Optional `publicOhttpRoutes: [{ port, upstream }]` listeners let the same stack serve its preparation, final-owner OHTTP and public discovery endpoints on additional ports of that IP using the same certificate. Each upstream is a fixed `http://<service>.<namespace>.svc:<port>` origin: port8445 is reserved for TNG OHTTP; port8083 is the operator's existing `<name>-access` public metadata Service. Routes cannot select raw Trustee/owner ports, paths, credentials or external hosts, and cannot reuse the guide's ports or the configured direct portal port. The owner must ensure the metadata Service exposes only its intended public routes. Network policy permits only the selected namespaces and backend target ports, including8083 for metadata. These proxies carry TNG ciphertext or public metadata; they do not terminate the initial guest RA-TLS connection or supply attestation authority.

DevOps prepares the workload's UID, mounts, ports, storage and reserved encrypted-image tag. Set `commandFromImage: true`, `imageKeyResource`, `browserOwner: true` and `accessLink.browser`; allow the exact access Secret in the operator. With `accessLink.browser.manualTls: true`, the Secret stores the frontend endpoint in `url` and the separately entered credential in `token`. The preparation VM generates the token at runtime; synthesis remains deterministic. Give the endpoint, token and registry push access separately. Keep the token out of the initial URL.

The user chooses an image and approves the stack in one page. The browser encrypts local image layers before upload. The preparation VM receives ciphertext and public OCI metadata, publishes the encrypted image and independently computes its final native policy without the image key. When the reserved tag appears, the operator verifies its encrypted layers, freezes the manifest digest and creates the final Pod. The browser verifies the resulting VM/workload measurement, enrolls its unique transport key, claims its unmodified Trustee and provisions image, disk and application keys. Disk keys go directly to the final Trustee. No user-created Kubernetes resources or administrator follow-up is needed.

For large images, DevOps sets `runtime.createContainerTimeoutSeconds` on the workload and a longer `runtimeRequestTimeout` in the node's native kubelet configuration. Kata downloads and decrypts confidential images during container creation, so its usual 60-second limit can expire before the application starts. Give the application an appropriate `containers[].resources` memory limit as well. Omitting the timeout preserves the runtime default and existing guest definitions.

Discovery is an untrusted metadata service. It holds disposable first-claim authority and public owner metadata. After enrollment, its token/URL are removed; later access requires owner signatures with a separate audience from Trustee authorization. The browser's trusted profile is part of its independently reviewed release, never downloaded as authority from discovery. An enrolled guest is never silently replaced.

The [complete stack example](../../../../example/confidential-workload-stack.ts) also supports the native CLI and raw TCP TNG/TLS owner route. Browser workloads add an HTTPS OHTTP route to `<name>-owner:8445`; the existing native owner port 8443 remains available. Owner endpoints are published before application readiness to avoid a key-provisioning deadlock. Ordinary application Services retain readiness gating.

`ConfidentialStorage` supports guest-only `Memory` and `EncryptedBlock` over an existing raw-block PVC. `ConfidentialStorageDevices` handles host device plumbing without a decryption key. The measured helper retrieves its key from local Trustee and opens LUKS inside the guest. `IfEmpty` formats only an entirely zero device; `Never` never formats. Retain PVCs and backing ciphertext. LUKS-XTS does not provide general disk integrity or rollback prevention.

The guest firewall and measured launcher keep application UIDs away from KBS, AA, CDH, the collateral proxy and owner interfaces. Applications can receive only explicit `applicationResources` through a peer-credential-checked private socket. Image and volume key paths cannot be delegated there. Bootstrap waits for owner policy and all declared resources. Owner diagnostics expose retrieval/storage status without resource bytes.

Administrators can deny service or claim an unused invitation first; the real client then refuses image/key upload. A second approved VM has a different instance key and an empty Trustee. Enrolled pins prevent silent substitution; global singleton enforcement, disk rollback resistance and automatic replacement custody remain outside scope. Running guest changes report `UpdatePending` and require owner enrollment of a replacement.
