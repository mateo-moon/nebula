# Confidential workloads

`ConfidentialOperator` installs the `ConfidentialWorkload` and `ConfidentialStorage` CRDs and a namespace-scoped controller. Each workload gets its own SEV-SNP PodVM with the pinned official Trustee Helm chart, TNG, owner gateway, storage helper and application. Native CoCo `genpolicy` measures the complete Pod. The operator never receives decryption keys or owner private keys.

For the installation-free user flow, add `ConfidentialBrowser`: a measured preparation VM with only guest-memory storage and no Kubernetes credentials or external Trustee. An independently hosted loader verifies its SNP evidence in TNG WASM, pins its transport key and fetches all UI assets through that attested channel. See the [browser guide](../../../../../confidential-browser/README.md) for deployment options and release qualification.

DevOps prepares the workload's UID, mounts, ports, storage and reserved encrypted-image tag. Set `commandFromImage: true`, `imageKeyResource`, `browserOwner: true` and `accessLink.browser`; allow the exact access Secret in the operator. The preparation VM generates a one-time token at runtime. The controller stores the resulting loader URL in the Secret's `url` entry. Synthesis stays deterministic. Give the user that URL and registry push access.

The user chooses an image and approves the stack in one page. The preparation VM encrypts/publishes the image and independently computes its final native policy. When the reserved tag appears, the operator verifies its encrypted layers, freezes the manifest digest and creates the final Pod. The browser verifies the resulting VM/workload measurement, enrolls its unique transport key, claims its unmodified Trustee and provisions image, disk and application keys. Disk keys go directly to the final Trustee. No user-created Kubernetes resources or administrator follow-up is needed.

Discovery is an untrusted metadata service. It holds disposable first-claim authority and public owner metadata. After enrollment, its token/URL are removed; later access requires owner signatures with a separate audience from Trustee authorization. The browser's trusted profile is part of its independently reviewed release, never downloaded as authority from discovery. An enrolled guest is never silently replaced.

The [complete stack example](../../../../example/confidential-workload-stack.ts) also supports the native CLI and raw TCP TNG/TLS owner route. Browser workloads add an HTTPS OHTTP route to `<name>-owner:8445`; the existing native owner port 8443 remains available. Owner endpoints are published before application readiness to avoid a key-provisioning deadlock. Ordinary application Services retain readiness gating.

`ConfidentialStorage` supports guest-only `Memory` and `EncryptedBlock` over an existing raw-block PVC. `ConfidentialStorageDevices` handles host device plumbing without a decryption key. The measured helper retrieves its key from local Trustee and opens LUKS inside the guest. `IfEmpty` formats only an entirely zero device; `Never` never formats. Retain PVCs and backing ciphertext. LUKS-XTS does not provide general disk integrity or rollback prevention.

The guest firewall and measured launcher keep application UIDs away from KBS, AA, CDH, the collateral proxy and owner interfaces. Applications can receive only explicit `applicationResources` through a peer-credential-checked private socket. Image and volume key paths cannot be delegated there. Bootstrap waits for owner policy and all declared resources. Owner diagnostics expose retrieval/storage status without resource bytes.

Administrators can deny service or claim an unused invitation first; the real client then refuses image/key upload. A second approved VM has a different instance key and an empty Trustee. Enrolled pins prevent silent substitution; global singleton enforcement, disk rollback resistance and automatic replacement custody remain outside scope. Running guest changes report `UpdatePending` and require owner enrollment of a replacement.
