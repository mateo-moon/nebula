# Confidential workloads

`ConfidentialOperator` installs the `ConfidentialWorkload` and `ConfidentialStorage` CRDs and a namespace-scoped controller. Each workload gets its own SEV-SNP PodVM with the pinned official Trustee Helm chart, TNG, one Nebula agent and the application. Set `agentImage` to the reviewed agent digest. Native CoCo `genpolicy` measures the complete Pod. The operator never receives decryption keys or owner private keys.

The [agent](../../../../../confidential-agent/README.md) has one main entrypoint and shared lifecycle. Owner access, readiness, attestation collateral, browser frontend and preparation are internal modules. Inside a workload guest, it replaces the separate owner, readiness, firewall, launcher-installation, resource-broker and per-volume containers. Its HTTP process drops to UID 10001 before listening. One private native child owns all declared encrypted volumes and approved application-resource sockets with only CHOWN, SYS_ADMIN and MKNOD capabilities.

TNG and the unmodified official Trustee remain upstream components. The Kubernetes controller remains outside the guest. Enrolled declarations using `storageImage` and `trustee.gatewayImage` retain their measured layout; use `agentImage` for new deployments rather than replacing an enrolled guest.

For the browser flow, add a `ConfidentialBrowser` preparation VM and a diskless frontend using `manualTls`. TNG serves the first page with TLS terminating inside the measured guest. The user independently checks the browser's actual certificate and approved workload measurements before entering their token. TNG WASM then verifies the preparation and final workload, with keys released only to their enrolled instances. See the [browser guide](../../../../../confidential-browser/README.md).

An optional `ConfidentialWelcome` adds a normal HTTPS connection guide at a literal public IP. Its own pinned Caddy sidecar handles Let's Encrypt HTTP01 and TLS, with the required `shortlived` certificate profile and automatic renewal; it uses no Ingress, cert-manager, DNS record or shared ingress controller. Set `name`, `namespace`, `ipAddress`, `acmeEmail`, an existing retained filesystem PVC in `acmeClaimName`, and the token-free guest `portalUrl`. Optionally supply `nodeSelector`, public reference measurements and a release URL. The stack's Service maps the supplied address on ports 80/443 to unprivileged Caddy listeners; that address must already route to the cluster, and both ports must be available. No load balancer or public IP is allocated by the module.

Node serves only on guest-independent Pod loopback `127.0.0.1:8081`; Caddy owns HTTP8080/HTTPS8443 and explicitly selects the IP certificate for clients without SNI. Both containers run without root, extra capabilities or Kubernetes credentials. Only Caddy mounts the private ACME state PVC at `/data`; retain that PVC and its backing volume across Pod replacement so account state, certificate keys and renewal information survive. A `Recreate` deployment avoids concurrent writers to the RWO claim. Storage provisioning and a suitable retention policy belong to the owning stack; there is no temporary certificate-state fallback. The public Service includes unready endpoints so the first HTTP01 challenge can succeed before HTTPS readiness. None of this changes confidential guests, their disks or their RA-TLS keys. Give users the guide's `https://<IP>/` URL and the access token separately.

The guide explains independent verification, displays a current reported certificate snapshot, and offers DER/evidence downloads before linking to the RA-TLS portal. Ordinary HTTPS authenticates the guide's IP address; it does not attest the guest. Users must verify and compare the portal's actual browser certificate against independently approved measurements before entering credentials. Optional certificate trust settings vary by browser and may leave hostname or other warnings. The guide never accepts access tokens, passwords, images or registry credentials. Its public API remains limited to one fixed guest-certificate route, with no caller-selected destination or owner API forwarding. For a frontend in the same cluster, set `portalService: { name, namespace }`: the server fetches public material through that ConfidentialBrowser's private Service on10443 and allows only its namespace/browser pod label in network policy. The public portal URL stays unchanged, and this private certificate origin is omitted from `GET /config.json`. Omitting `portalService` retains the external public-origin relay.

Optional `publicOhttpRoutes: [{ port, upstream }]` listeners let the same stack serve its preparation, final-owner OHTTP and public discovery endpoints on additional ports of that IP using the same certificate. Each upstream is a fixed `http://<service>.<namespace>.svc:<port>` origin: port8445 is reserved for TNG OHTTP; port8083 is the operator's existing `<name>-access` public metadata Service. Routes cannot select raw Trustee/owner ports, paths, credentials or external hosts, and cannot reuse the guide's ports or the configured direct portal port. The owner must ensure the metadata Service exposes only its intended public routes. Network policy permits only the selected namespaces and backend target ports, including8083 for metadata. These proxies carry TNG ciphertext or public metadata; they do not terminate the initial guest RA-TLS connection or supply attestation authority.

DevOps prepares the workload's UID, mounts, ports and storage. For direct browser upload, enable the built-in image store described below; no user registry account or destination is needed. Set `commandFromImage: true`, `imageKeyResource`, `browserOwner: true` and `accessLink.browser`; allow the exact access Secret in the operator. With `accessLink.browser.manualTls: true`, the Secret stores the frontend endpoint in `url` and the separately entered credential in `token`. The preparation VM generates the token at runtime; synthesis remains deterministic. Give the endpoint and token separately. Keep the token out of the initial URL.

The user chooses a local image or an optional external registry source and explicitly approves its complete application contract: command/arguments, environment overrides, identity, mounts, resource access, ports and network. A reviewed runtime profile approves helper software, not administrator-selected application behavior. Without an explicit command override, execution derives from the owner's digest-bound OCI image. Native policy binds literal process values; application/image environment placeholders cannot introduce host-selected values.

The browser encrypts image layers before upload. The preparation VM receives ciphertext and public OCI metadata, commits the encrypted image to the stack's store and independently computes its final native policy without the image key. When the complete release is available, the operator verifies its encrypted layers, freezes the manifest digest and creates the final Pod. The browser verifies the resulting VM/workload measurement, enrolls its unique transport key, claims its unmodified Trustee and provisions image, disk and application keys. Disk keys go directly to the final Trustee. No user-created Kubernetes resources or administrator follow-up is needed.

## Built-in image storage

The image store is an optional module in the existing operator process. Supply a dedicated filesystem PVC to the operator; it holds encrypted image layers and public OCI metadata. Owner state and all usable image/disk keys stay outside that PVC. Use `ConfidentialStorage` for the application's encrypted disks or memory, and an ordinary retained filesystem PVC for these already-encrypted image bytes.

For namespace `example` and workload `application`:

```ts
const imageStore = {
  endpoint: "http://confidential-operator-images.example.svc:8084",
  writeEndpoint: "http://confidential-operator-images.example.svc:8085",
  repository: "example/application",
};

new ConfidentialOperator(chart, "operator", {
  namespace: "example", watchNamespaces: ["example"], image: images.operator,
  imageStore: {
    claimName: "application-images", repository: imageStore.repository,
    maxBytes: 8 * 1024 ** 3,
    preparationPodSelector: { "confidential.nebula.dev/browser": "preparation" },
    nodeRegistryHostsDirectory: "/etc/containerd/certs.d",
  },
  accessLinkSecrets: [{ namespace: "example", name: "application-access" }],
});
```

Pass the same `imageStore` tuple to the preparation `ConfidentialBrowser` and the `ConfidentialWorkload.spec`. Set the application's image to `imageStoreImage(imageStore)`, imported from `nebula-cdk8s/confidential-workloads`. The diskless frontend does not receive the store configuration. Endpoints must name one internal Service on ports 8084/8085; the repository must equal the workload's namespace/name. The preparation guest compares this tuple with its measured configuration before accepting a connection.

Port 8084 serves immutable OCI image content; port 8085 accepts publication only through the exact preparation Pod's private network route. The preparation API accepts only ciphertext uploads and application approval. Native CoCo pulls the encrypted image through the store's OCI API. HTTP is scoped to that exact internal repository in the publisher/operator and native genpolicy transport; CDH's guest pull routing is separately included in measured Init-Data. External registries keep certificate verification. No image-store service needs a decryption key or an external bootstrap Trustee.

Kubelet/containerd also fetches image metadata on the node before guest pulling starts. A cluster-only Service name and HTTP transport therefore need a matching node-side registry mapping. Set `imageStore.nodeRegistryHostsDirectory` to the directory the node's CRI already uses for native per-registry `hosts.toml` files. On Linux, containerd 2.3 defaults to `/etc/containerd/certs.d:/etc/docker/certs.d` when its loaded path and mirrors are empty; the first directory is appropriate for the example. See the [containerd host configuration](https://github.com/containerd/containerd/blob/v2.3.3/docs/hosts.md). This option requires the default operator name, `confidential-operator`, so its authority matches the native `CONFIDENTIAL_OPERATOR_IMAGES_SERVICE_HOST` Service environment variable.

This opt-in adds one init container using the operator image. It writes only this store's authority subdirectory, mapping it to the private Service IP, then exits. The root init has no API-token mount; the nonroot manager retains its rotating, read-only projected API credentials and never mounts the host directory. The store Service and NetworkPolicy share the operator's Argo wave so native Service metadata can be available at startup. A retained `WaitForFirstConsumer` ciphertext PVC must also share its actual consumer's wave. No runtime configuration, other registry, external port or daemon restart is required. The mapping handles untrusted ciphertext/public-metadata transport; enrolled guest policy, image integrity checks and key release remain authoritative. Omitting the option preserves the previous deployment bytes for clusters whose node transport is already configured.

The init configures only the node hosting the operator. Pin the store PVC/operator to the same node as the final workload, using the filesystem StorageClass's topology, or provide the corresponding native mapping on every consumer node. The option does not configure an entire cluster. Preserve the Service identity and ClusterIP while its mappings are in use.

The store publishes its `release` tag only after every referenced object is complete and hash-checked. Repeating the same publication is safe; replacing that tag with different content is refused. Retain the PVC across operator replacement. Administrators may delete or withhold ciphertext, but different bytes cannot satisfy the owner-approved digest and policy. Existing declarations without `imageStore` retain their external-publication path and measured layout.

The optional registry source is downloaded over browser-verified HTTPS through an opaque byte relay. Registry login credentials and source-image decryption keys/passwords remain on the user's computer. Encrypted source layers are authenticated before local decryption, then re-encrypted under a fresh destination key. Large source blobs require exact HTTP Range support; unsupported servers produce a clear local-archive fallback. See the [browser guide](../../../../../confidential-browser/README.md) for supported source-key formats and limits.

For large images, DevOps sets `runtime.createContainerTimeoutSeconds` on the workload and a longer `runtimeRequestTimeout` in the node's native kubelet configuration. Kata downloads and decrypts confidential images during container creation, so its usual 60-second limit can expire before the application starts. Give the application an appropriate `containers[].resources` memory limit as well. Omitting the timeout preserves the runtime default and existing guest definitions.

Discovery is an untrusted metadata service. It holds disposable first-claim authority and public owner metadata. After enrollment, its token/URL are removed; later access requires owner signatures with a separate audience from Trustee authorization. The browser's trusted profile is part of its independently reviewed release, never downloaded as authority from discovery. An enrolled guest is never silently replaced.

The [complete stack example](../../../../example/confidential-workload-stack.ts) also supports the native CLI and raw TCP TNG/TLS owner route. Browser workloads add an HTTPS OHTTP route to `<name>-owner:8445`; the existing native owner port 8443 remains available. Owner endpoints are published before application readiness to avoid a key-provisioning deadlock. Ordinary application Services retain readiness gating.

The [native client](../../../../../confidential-client/README.md) requires an independently reviewed `application-approval` document before `deploy`. It uses a private local Unix socket and qualified TNG builtin appraisal of each live outer TLS certificate before forwarding owner bytes; no local Docker AS or shared TCP verifier listener runs. Enrolled inner certificates may renew only with the same instance public key. The optional local UI prints its private session URL for manual opening. Legacy AS preparation files remain compatibility state. The optional public VCEK cache is used by builtin appraisal with AMD chain, report signature and chip/TCB checks retained.

`ConfidentialStorage` supports guest-only `Memory` and `EncryptedBlock` over an existing raw-block PVC. `ConfidentialStorageDevices` handles host device plumbing without a decryption key. The measured helper retrieves its key from local Trustee and opens LUKS inside the guest. `IfEmpty` formats only an entirely zero device; `Never` never formats. Retain PVCs and backing ciphertext. LUKS-XTS does not provide general disk integrity or rollback prevention.

The guest firewall and measured launcher keep application UIDs away from KBS, AA, CDH, the collateral proxy and owner interfaces. Applications can receive only explicit `applicationResources` through a peer-credential-checked private socket. Image and volume key paths cannot be delegated there. Bootstrap waits for owner policy and all declared resources. Owner diagnostics expose retrieval/storage status without resource bytes. Unified agent layouts also support the enrolled owner's `diagnostics` command: fixed KBS error-category counters from a bounded private guest-memory log window, never raw logs or tokens. Only the agent mounts that KBS temporary volume, read-only; applications do not receive it. Existing legacy layouts and standalone Trustee logging remain unchanged.

## Dedicated public application address

`ConfidentialPublicAddress` maps an existing public IPv4 on one Linux host to the final workload's current ready SNP Pod. It forwards all TCP and UDP ports and uses that same public address for Internet egress. Supply `name`, `namespace`, `nodeName`, `ipAddress`, `workloadName`, `profile`, the cluster's private `podCidr`, and a pinned utility `image` containing Node 24 and `nft` (the workload agent image contains both). Allocate the address exclusively: do not also put it in a Kubernetes Service or another NAT rule.

This is ordinary host routing, outside the confidential guest. A single `Recreate` deployment has only `NET_ADMIN`, no host filesystem mounts, and read-only Pod-list credentials for its own namespace. It updates only its allocation's named nft table. It selects one ready, non-terminating `kata-qemu-snp` Pod with the exact workload/profile labels on the configured node. Missing, ambiguous, unready or unavailable API state removes the mapping and rejects traffic to the allocated address; an API request has a ten-second bound and reconciliation runs every two seconds. Guest `hostNetwork`, measured genpolicy, encryption and owner enrollment remain unchanged. The host may still deny service or reroute packets, so this address never replaces attestation or the enrolled transport key.

The construct's NetworkPolicy allows all ingress and egress only for the selected workload labels. Preparation, discovery and image-store policies retain their separate selectors and restrictions. Private guest services remain bound to guest loopback and protected from application UIDs. TNG owns TCP 8443 and 8445 inside the final guest; these remain authenticated system ports and cannot simultaneously be application listeners. Use a separate IP for the welcome/portal services to leave application ports 80 and 443 available. Port forwarding alone does not make an application listener healthy.

The node must already route the public address, have `nft`, IPv4 forwarding and a compatible CNI path; no global firewall, Cilium configuration or runtime is changed. The table uses DNAT priority -110 and SNAT priority 90, preceding the usual -100/100 service NAT chains. Verify both directions on the target node because an existing host firewall or CNI program can still reject or transform traffic. Shutdown leaves this allocation's inactive rejection table in place to avoid exposing wildcard host listeners. When retiring the allocation, first stop its routing deployment, then explicitly remove only its reported `tableName` before reassigning the IP.

The measured Pod supplies empty Kubernetes API service variables instead of inheriting a host-selected API endpoint. Explicit image or owner environment values retain precedence. Native policy requires every literal environment value and rejects additional names or changed values; identical duplicates from native image/Pod merging do not alter that requirement.

Unified agents automatically prepare public SNP collateral before owner access. A dedicated 1 MiB guest-memory volume contains only bounded public DER for the current chip and TCB; the agent writes it, native KBS mounts it read-only, and applications never mount it. Native `OfflineStore` verification retains AMD chain, report signature, chip, TCB and policy checks. Failure to obtain or safely publish collateral leaves startup unready; there is no hidden KDS fallback in KBS. No manual certificate artifact or additional Trustee service is required.

Administrators can deny service or claim an unused invitation first; the real client then refuses image/key upload. A second approved VM has a different instance key and an empty Trustee. Enrolled pins prevent silent substitution; global singleton enforcement, disk rollback resistance and automatic replacement custody remain outside scope. Running guest changes report `UpdatePending` and require owner enrollment of a replacement.
