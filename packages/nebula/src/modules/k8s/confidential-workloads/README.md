# Confidential workloads

`ConfidentialOperator` installs the `ConfidentialWorkload` and `ConfidentialStorage` CRDs and a namespace-scoped controller. Each workload gets its own SEV-SNP PodVM with the pinned official Trustee Helm chart, TNG, owner gateway, storage helper and application. The controller renders the final Pod through native CoCo `genpolicy`; the owner independently renders the same public declaration and verifies the result through TNG before releasing any key. The controller never holds owner credentials or plaintext keys.

The [complete Nebula example](../../../../example/confidential-workload-stack.ts) shows the namespace, operator, ciphertext disk, NRI device helper, storage declarations, workload and a TCP pass-through owner route. Replace its illustrative images, SNP identity, node, network, disk allocation, gateway class and claim hash with reviewed values before deployment.

DevOps predeploys a `ConfidentialWorkload` with a reserved image tag, `imageKeyResource` and `commandFromImage: true`. Supply a temporary `accessToken` deployment parameter containing 32 random bytes encoded as 64 hex digits. The construct hashes it before storing its configuration; only `ownerClaimSha256` enters Kubernetes and native measurement. Give the token and public connection settings to the user. No invitation-file command or owner public key is needed during setup. GitOps installations can keep the resulting public commitment as a literal so subsequent synthesis stays deterministic; never commit the plaintext token.

Until the image is published, the controller retries rendering and creates no Pod. After publication it verifies every encrypted layer, resolves the tag to a digest, and derives Entrypoint + Cmd from OCI configuration whose hash is bound to that manifest. Native `genpolicy` measures the complete resulting Pod. The owner client independently measures its verified publication and refuses a different guest. The image needs an absolute executable path and must fit the prepared UID, mounts and service ports; these are shown in the UI. The administrator does not need to customize its command or provision keys.

Users run `confidential-client ui`, load the connection settings, choose a local image and enter the token. The local service handles encryption, publication, attestation, first claim and key provisioning. Like a local signer, it keeps owner credentials on the user's computer. Subsequent operations require the owner's P-256 JWT, not the temporary token. See the [client guide](../../../../../confidential-client/README.md).

`ConfidentialStorage` offers guest-only `Memory` or `EncryptedBlock` over an existing raw-block PVC. `ConfidentialStorageDevices` supplies host device plumbing without a decryption key. For block storage, the measured helper fetches the owner-provisioned key from local Trustee and opens LUKS inside the guest. `IfEmpty` formats only an entirely zero device; `Never` never formats. The PVC and backing file remain ciphertext. Retain and protect them from GitOps pruning. LUKS-XTS does not provide general disk integrity or rollback prevention.

The guest firewall and measured static launcher keep application UIDs away from KBS, AA, CDH and the owner gateway. An application can receive only explicit `applicationResources` through a peer-credential-checked private socket. Image and volume key paths cannot be delegated there. Bootstrap waits for owner policy and every declared resource before the application starts. The owner can read retrieval and storage diagnostics without resource bytes.

The controller never replaces a running enrolled Pod silently. A declaration or renderer change reports `UpdatePending`; the owner must approve and enroll a replacement. An identical second VM still has a different guest TLS key and empty Trustee, but a user can explicitly approve and provision multiple instances. Neither this module nor native CoCo enforces a global singleton. An administrator who knows the unclaimed invitation can claim first and deny service; the real user's client refuses to upload keys unless its own key controls the attested guest. Kubernetes status and names are operational data, not attestation evidence.

The operator creates `<name>-owner` with only port 8443 and publishes its endpoint before application readiness, so owner provisioning cannot deadlock on the encrypted application. Route owner TCP traffic to that Service. The ordinary `<name>` Service keeps readiness gating for application traffic.
