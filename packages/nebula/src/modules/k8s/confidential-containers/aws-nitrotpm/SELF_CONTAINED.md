# Self-contained AWS CoCo module

The managed implementation lives in `../aws-coco-managed.ts`, `control/`,
`guest/src/boot.rs`, `guest/src/evidence/`, `guest/src/authority/replication/`
and `release/`. It replaces the prototype's manual installation procedure.
Software integration tests pass and a public candidate release is available;
complete immutable-appliance hardware qualification and promotion into the
default catalog remain pending.

## Installation contract

Declare the reusable module, apply its normal Nebula deployment, and wait for
`kata-remote-aws-nitrotpm`. The only cloud placement inputs are the platform VPC,
worker security groups and optional existing provider/region selection.
Public owner enrollment is generated by the trusted owner's normal release
build using `createAwsCocoEnrollment()`. Its private signer is never sent to
Kubernetes. No Python program is a module-user installation step.

The module owns and discovers its IAM users/policies/credentials, guest role,
instance profile, artifact bucket, image snapshots/AMIs, additional subnets and
routes, network rules, interfaces/addresses, authority replicas/state volumes,
runtime launch template and encrypted installation probe. It uses the existing
Nebula AWS provider account. The default economy placement is eu-west-1 with
three c6a.large authority instances; each workload gets its own c6a.large PodVM.
Public IPs provide registry egress without requiring a separately operated NAT.
The authority's publisher endpoint authenticates signed owner operations;
replica traffic and PodVM transport have separate restricted network rules.
The module also installs the peer-pod CRD and manages admission certificates
without an external cert-manager. Renewal publishes overlapping CA trust before
changing the serving key, and removes old trust only after every webhook replica
finishes its rollout. Persisted checkpoints make interrupted renewal resumable.
Admission intercepts only this module's RuntimeClass and keeps fail-closed
behavior; unrelated Pods and the controller can start while TLS is being set up.
These Kubernetes-visible TLS keys protect admission transport, not workload data.

## Where the automatic steps happen

| Step | Execution location | Management-visible result |
| --- | --- | --- |
| Build and release generic appliances | Nebula software release pipeline | Immutable disk/client/image digests and offline UKI measurements |
| Import images and provision infrastructure | Module controller plus existing AWS provider | Owned cloud IDs and public operation cursors |
| Enroll authority and recover replicas | Measured authority VMs with TPM-protected journals | Attested group identity, peers and quorum health |
| Bind policy, obtain keys and start runtime | Measured PodVM, attested authority, stock Kata/CDH/APF | Readiness and normal Pod status |

The software publisher builds images once per release. Module consumers do not
operate a build service or supply first-observed measurements. A candidate
release is not automatically a qualified/default release: the exact catalog is
promoted only after hardware/lifecycle acceptance. Rebuilding a candidate may
change its artifact/PCR identity and requires qualification of those exact bytes.

## Owner authorization and key boundary

The deployment ID commits canonical owner-signed genesis: owner keys/threshold,
authority release, allowed runtime release and a stable deployment nonce.
An owner publisher authenticates fresh evidence and persists the original
protected authority identity before sending any image keys. Keys go directly
to the attested service, never through a ConfigMap, Secret, controller or CR.

Every workload grant binds that original authority identity, deployment,
workload, generation, exact descriptor SHA384, runtime release and commitments
to the exact AES-256 image-key resources. The descriptor binds the immutable
images and policy bytes. Rotation/revocation commit in the same protected state
as replication membership; a stale leader cannot authorize after a new majority
commits a change. No authorization lease or host clock replaces the quorum read.

The guest checks current attested approval before installing policy, extends
SHA384 PCR15 once, confirms the measurement and opens a fresh mutually attested
channel to obtain the scoped keys. A failure before intent arrives can retry;
a failure after policy activation cannot silently extend again or replace it.
The stock offline filesystem KBC reads keys from a private, nonswappable tmpfs.
Decrypted image storage is also volatile. Mutable CAA data supplies validated
network/TLS transport only; it cannot install policy, commands or credentials.

The installation canary is a fixed release-built encrypted image/policy with a
well-known public test key in a reserved namespace. The measured authority signs
its public intent. Customer owners cannot overwrite that workload slot, and the
canary does not import or share customer keys. Controller readiness waits for
its successful ordinary Kata Pod. Readiness remains informational and is never
an authority authorization input.

## Attestation and protected recovery

The measured collector obtains a local AMD SNP/VLEK report bound to the channel
key and encloses its digest/claims in fresh NitroTPM COSE evidence. Peers verify
the pinned AWS/AMD roots, release PCR4/PCR12, role, firmware floor, nonce,
deployment, channel certificate and runtime policy PCR15. The TLS 1.3 handshake
on the same socket must prove possession of that attested channel key. Public
publisher connections have a separate protocol/port; their authorization comes
from signed application messages, not a client certificate supplied by an admin.

This locality argument explicitly trusts AWS Nitro. It does not independently
compose SNP and TPM evidence against a malicious hypervisor. AWS account and
Kubernetes administrators remain outside the key boundary. They may replace
controllers or public discovery, copy encrypted disks and deny service; those
powers do not confer owner signatures, a measured guest identity, an original
lineage or a fresh quorum.

Three OpenRaft replicas persist votes, logs, membership, owner history and key
state through one encrypted TPM-sealed/NV-anchored journal. Acknowledgment follows
confirmed persistence. The local journal retains current/previous ciphertexts;
cloning, rollback, clearing, wrong boot/deployment and uncertain commits fail
closed. Preserved-instance restart keeps the TPM and original group identity.
Replacement uses a new local TPM/disk, attested learner catch-up and joint
membership, with one protected replacement at a time. Losing the last usable
quorum stops authorization; deleting every sealed copy makes keys unrecoverable.
No management recovery password or operator-readable key backup exists.

## Reconciliation and deletion

The controller acquires a Kubernetes Lease for infrastructure work only. Public
cursors record image-import completion receipts and idempotency intents before
cloud mutations. Retries do not re-upload a completed snapshot or allocate a
second state volume after losing an AWS response. API inventories paginate;
foreign/ambiguous ownership is refused. Credential changes automatically roll
CAA/cleanup, while the controller reads its projected credential files afresh.
Git declares static CAA settings only. Discovered cloud IDs and rollout stamps
belong to the controller, so normal GitOps reconciliation preserves them without
requiring application-level ignore rules.

The CR finalizer remains until owned cloud resources have disappeared, including
instances, imported images/snapshots, state disks, interfaces, addresses, network
rules and boot storage. Existing platform VPCs, worker groups and gateways are
preserved. Nebula's ordered sync/prune keeps the controller/credentials available
while cleanup runs. Do not force-remove finalizers or tear down the platform
provider first. Those destructive administrative actions cannot be repaired by
a controller that no longer exists.

Release/enrollment changes are immutable. A software upgrade must first add an
authenticated release transition; replacing the authority AMI in place is
rejected. This version supports restart and member replacement, not automatic
cross-release migration. The old prototype AMI API remains a research interface.

## Evidence and acceptance

Local validation includes real synthetic COSE/SNP signatures and certificate
chains, real TLS with channel-key substitution rejection, actual OpenRaft
elections/snapshots/partitions/replacement, TPM journal fault injection, Node/Rust
signed-contract interoperability, AWS SDK request-shape tests, controller failure
paths and real Helm synthesis. The complete Linux fixture currently passes 64
Rust tests, including software-TPM tests. These tests do not qualify AWS firmware,
EC2 persistence guarantees, the full boot services or end-to-end isolation.

The assembled Linux appliances also pass offline systemd dependency checks and
start their bootstrap executables using the libraries included in each image.
The CI-built Apple Silicon owner client passes the Node/Rust signed-contract
checks. The published candidate passes anonymous download checks for both disks,
all three owner clients and
all four container manifests, including compressed and expanded disk digests.
Live Kubernetes validation accepts the managed resource schemas and
rejects a changed immutable enrollment. The real AWS provider creates the scoped
test users, policies and credential Secrets, and ordinary Crossplane deletion
removes the fixture's users, role, instance profile and policies. The actual
EBS sparse uploader passes encrypted snapshot completion and byte/checksum
readback. These checks remain separate from complete attested guest boot and
recovery acceptance.

Argo CD 3.3.0's diff engine preserves controller-discovered cloud IDs and restart
annotations in the rendered resources with both client-side and server-side
apply. Negative checks reproduce drift from the old empty placeholders and
still detect changes to declared security settings.

The controller suite includes real admission TLS hostname verification and
lost-response recovery at each certificate-rotation checkpoint. Live deployment
also verified creation of all module IAM resources, including the guest role's
instance-profile attachment. Full hardware acceptance remains pending below.

Release acceptance requires actual generic authority/runtime boot, three-replica
attested enrollment, encrypted canary, controller restart during import,
service restart, preserved-instance reboot/stop-start, failed-member replacement,
quorum loss refusal, tampered policy/profile refusal and complete owned-resource
removal. The earlier [hardware experiment](HARDWARE_QUALIFICATION.md) establishes
local TPM mechanics only; it is not evidence that these new appliances passed.
