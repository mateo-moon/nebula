# Immutable guest build candidate

Base: Amazon Linux `kiwi-image-descriptions-examples` commit `4570f0ec8c9217f77c81ed79cb4200cbf9e40912`, `kiwi-image-descriptions-examples/al2023/attestable-image-example`. Read its README for supported AL2023 KIWI build/import commands. This repository provides a local staging overlay, not an AMI deployment script.

`prepare_image.py` creates a fresh KIWI description from that exact checkout, installs reviewed policy/bootstrap/endpoint CA and SHA256 checked binaries, removes the stock writable root overlay and zram swap, and masks mutable CAA user-data processing, disk scratch, remote login and debugging. No key material belongs in the build inputs. `policy.rego` must be the workload's reviewed generated policy, not a default allow policy. Boot services require successful attested-key provisioning.

**The output deliberately cannot run stock CAA yet.** CAA requires user-data transport/network setup, currently masked because its unrestricted implementation can replace guest policy/CDH settings. A restricted provisioner and memory-only scratch implementation are required before enabling cloud integration. KIWI erofs/dm-verity boot without its default overlay is also unbuilt here. Check the final initramfs, `/proc/cmdline`, root mount, service graph and actual Kata configuration; file staging alone proves none of these properties.

`agent.toml`'s `policy_file` support and precedence relative to `agent.policy_file` kernel settings must be qualified against the final pinned Kata binary. Build that binary with `AGENT_POLICY=yes` and the same policy as its `DEFAULT_AGENT_POLICY_FILE`; record its source revision and digest. Unknown or ignored TOML fields must block qualification. No policy or init-data annotation may provide a replacement. The image marker records `deployment_enabled=false` and is included in the measured root.

After a successful offline Linux image build, run pinned NitroTPM-Tools `nitro-tpm-pcr-compute --image <UKI.efi>`. `approved_profile.py` converts its SHA384 PCR4/12 output and the exact policy bytes into a review candidate with `reviewed=false`. An independent image reviewer must verify the root hash binds all staged assets, eliminate command-line/config/overlay overrides, run the negative boot/runtime tests, then approve the profile. CAA has no permission to approve measurements or KBS policy.

Use a dedicated nonswappable tmpfs for secrets and **all decrypted image layers/application confidential state**. The existing CAA disk scratch service is masked here. Apply resource limits and verify that snapshots, root block devices and shutdown diagnostics contain no decrypted data. Guest API authentication also needs an embedded policy for intended callers; account-owner security group rules alone do not establish that boundary.
